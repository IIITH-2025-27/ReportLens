ReportLens · the workflow in detail

How ReportLens checks a report

This page follows the code from start to end. For every stage it says what happens, the rules the stage follows, and the maths it uses, with real numbers taken from the calibration files. Start with the flowchart. Every box in it is a link to the stage that explains it.

Which version is described

The current code, run with configs/exp/v5.yaml. That is the setting the lite web app uses: rules read the sentence first, the AI model reads it only when the rules fail, and the "informed" planner picks the tools. Steps added after the 9 Nov freeze carry a tag such as v4+. With the frozen setting configs/exp/local_real.yaml every tagged step is switched off, so the frozen headline numbers stay reproducible.

The whole flow

In plain words

There are two halves. Once, before use, four reading tools read hundreds of chart points whose true values are known. From that, the helper learns two things: how big its reading error can be (the margin factors) and which tools can check each other (the tool and pair profile). For every report, the helper finds each number sentence, finds its chart, asks a trustworthy pair of tools to read the value, and lets a fixed formula decide. Nothing is learned while a report is checked.

Half 1

Before use: learning how far to trust each tool

Stages 1 to 4 run once (chart-claim-verifier calibrate). Their two output files are read later by the planner (stage 11) and the decision rule (stage 14).

1

Practice reports with an answer key

Plain code
generator/tables.pygenerator/plot.pygenerator/claims.pygenerator/injections.pygenerator/report_builder.py
In plain words

To know whether the helper is right, the true value behind every chart point must be known. Real reports do not come with that. So a program writes practice reports and the answer key at the same time, like a teacher who writes the exam and the solutions together.

What happens

  1. Each report gets 2 to 4 result tables: model names (ResNet-50, GRU, BERT-base…) against epochs or datasets, with accuracy, F1 or loss. Half the charts are drawn "hard": small, compressed, with many lines (generator.hard_share: 0.5).
  2. Each table is drawn as a line, bar or grouped-bar chart in varied styles, some saved as low-quality JPEG.
  3. For every figure 2 to 4 sentences are written, of these kinds: correct and exact (20%), correct but rounded such as "about 80%" or "over 80%" (20%), a planted mistake (35%), a mix-up of line or point (10%). Each report also gets sentences about models that no chart shows, and setup sentences such as "batch size 64".
  4. 15% of reports hide an instruction in tiny white text, each with a clean twin, for the safety test.
  5. The PDF, the figure images and truth.json are saved under data/local/generated/<set>/<id>/.
Rules
  • The answer key uses the same rounding function the checker uses (stage 8). "Correct" means correct within the rounding that the wording allows.
  • A "correct" sentence that falls outside its own rounding by accident, or a planted mistake too small to be wrong, is relabelled so the key is never inconsistent.
  • Every report has its own random seed, so no table appears in two sets.
Maths
planted value = true value + δ × span δ ∈ {±0.02, ±0.05, ±0.10, ±0.20, ±0.50} a sentence is correct when: approx |claimed − true| ≤ tol greater true > claimed "over 80%" less true < claimed "under 80%" between low − tol ≤ true ≤ high + tol "between 85% and 90%"
Worked example

True value 84.37 on an axis from 50 to 100 (span 50). With δ = +0.05 the planted value is 84.37 + 0.05 × 50 = 86.87, written "reaches 86.9%". Its rounding is ±0.05, and |86.9 − 84.37| = 2.53 is far above it, so the key says error.

2

All four tools read every calibration point

AI model call
calibration/collect.pypipeline.calibratecache/local.sqlite
In plain words

Before trusting a kitchen scale, you weigh things whose weight you already know. Here every one of the four tools reads every point of 51 practice charts (sets calib and calib_easy, 17 reports). That is 1,063 points. For each reading the program writes down how far off it was.

What happens

  1. For every chart, every line or bar group, and every x value: ask each tool for the value. Keep the value, or the error code if the tool refused, and the seconds it took.
  2. Turn every value into a signed error measured as a share of the true axis height, so a big chart and a small chart can be compared.
  3. Also note for each point: the chart's situation key (stage 6), whether the x value has its own tick label, and each tool's failure code.
  4. Build calibration items. Every point is one item of type "point". On top of that, about half as many random differences are made per chart (two lines at one x, or one line at two x values), and for line charts in percent, random relative changes. Each tool computes its own difference from its own two readings. An item needs at least two tools that answered. Result: 1,527 items.
Maths
error of tool t on a point: e_t = (v_t − truth) ÷ span derived items, one value per tool: difference_t = a_t − b_t relative change_t = (b_t − a_t) ÷ |a_t| × 100 tied legs: if a_t = b_t the tool gives no value (it probably read one point twice)
Worked example

True value 72.0, span 50. ocr_pixel reads 72.3, so e = 0.3 ÷ 50 = +0.006 (0.6% of the axis). vlm_crop reads 74.0, so e = +0.040 (4% of the axis).

3

Margin factors: how wide the error margin must be

Fixed rule or maths
calibration/fit.pycalibration/store.pycalibration/pvalues.pycalibration_tables/local/<tools>.json
In plain words

The helper wants a rule like "the true value is almost always within X times the tools' disagreement of the middle reading". To find X, every practice item is asked: how far was the middle reading from the truth, measured in units of disagreement? All these numbers are sorted. The number below which 75% of them fall is the accept factor. The number below which 95% fall is the flag factor.

What happens

  1. For each item and each k from 2 up to the number of tools that answered (at most 4), take the first k answering tools in the fixed order ocr_pixel, deplot, vlm_table, vlm_crop (calibration.order: fixed).
  2. Compute the ratio r for that set of k values.
  3. Store r in four groups at once, from specific to general: chart type | claim type | k, chart type | * | k, * | * | k and * | * | *.
  4. Sort every group and save it.
  5. At check time, use the most specific group that has at least 30 ratios and at least 20 different charts. Otherwise fall back to the next, more general group.
Maths
est = median(v₁ … v_k) MAD = median(|vᵢ − est|) r = |truth − est| ÷ (MAD + 0.005 × span) cut-off at level L (L = 0.75 or 0.95), ratios sorted from small to large, n ratios: q_L = the ⌈(n + 1) × L⌉-th smallest ratio if ⌈(n + 1) × L⌉ > n, then q_L = ∞ (too few ratios: that group can never decide) fallback order: line|point|k2 → line|*|k2 → *|*|k2 → *|*|*

The "+1" in ⌈(n + 1) × L⌉ is the small correction from conformal prediction. It makes the 95% promise hold on new charts that look like the practice charts, not only on the practice charts themselves.

Worked example: one ratio

Truth 80.0, span 50. ocr_pixel reads 80.3 and deplot reads 79.9. Then est = 80.1, MAD = 0.2, floor = 0.005 × 50 = 0.25, so r = |80.0 − 80.1| ÷ (0.2 + 0.25) = 0.1 ÷ 0.45 = 0.22.

A worse item: truth 80.0, readings 80.2 and 83.0. Then est = 81.6, MAD = 1.4, r = 1.6 ÷ 1.65 = 0.97. The tools disagreed, so the margin will be wide, and the truth was still inside about one disagreement.

Worked example: one cut-off

Group line|point|k2 holds n = 514 ratios from 24 charts, enough to be used. For 95%: ⌈515 × 0.95⌉ = ⌈489.25⌉ = 490, so q95 is the 490th smallest ratio = 1.867. For 75%: ⌈515 × 0.75⌉ = ⌈386.25⌉ = 387, so q75 = 0.889.

Honest note

The k = 2 groups are built mostly from the first two tools that answered (often ocr_pixel and deplot), not from the exact pair the planner later picks. Margins learned per exact pair were tried (run log U14) and gave more false flags (dev 1.4% → 4.1%), so the pooled margin stays. A pair that stopped early because it agreed is a selected sample, and the pooled margin is the buffer against that.

4

Tool and pair profile: who to ask, and which pairs can check each other

Fixed rule or maths
evaluation/tool_profile.pyevaluation/correlation.pycalibration_tables/local/<tools>.profile.json
In plain words

Stage 3 says how wide the margin is. This stage says who to ask. It is built from the same 1,063 calibration points, in two parts: each tool on its own, and each pair of tools together.

Pairs matter because the decision rule only answers when at least two readings exist, and two readings that agree shrink the margin. Agreement is only reassuring if the two tools do not make the same mistakes. Two witnesses who copy each other are worth one witness.

4a · Each tool on its own, per situation

Points are grouped by the situation key of their chart (line|easy, line|hard, bar|easy, bar|hard, and * for all). For each tool and group:

4b · Each pair of tools: "wrong when agreeing"

For every pair of tools (6 pairs) and every situation, the program looks only at points where both tools answered, and counts:

Maths
both = points where a and b both returned a value agree = of those, points with |e_a − e_b| ≤ 0.03 (within 3% of the axis) agree_wrong = of the agreeing points, those with |(e_a + e_b) ÷ 2| > 0.05 (their average still off by more than 5%) W(a,b) = agree_wrong ÷ agree "wrong when agreeing" charts, charts_wrong = how many different charts those points sit on

The 3% "agree" bar is the same number as the accept cap of the decision rule (decision.max_accept_margin), and the 5% "badly wrong" bar is the usual chart-reading tolerance (agent.informed.big_error).

Worked example: three points for the pair ocr_pixel + vlm_crop

Span 50, true value 70.

  • ocr_pixel 70.5 (e = +0.010), vlm_crop 71.0 (e = +0.020). |0.010 − 0.020| = 0.010 ≤ 0.03 → agree. Average error 0.015 ≤ 0.05 → a right agreement.
  • ocr_pixel 73.0 (+0.060), vlm_crop 73.5 (+0.070). Difference 0.010 → agree. Average 0.065 > 0.05 → a wrong agreement. Both tools fooled the same way.
  • ocr_pixel 70.5 (+0.010), vlm_crop 74.0 (+0.080). Difference 0.070 > 0.03 → not an agreement. It counts neither way, because the decision rule would see a wide disagreement here and widen its margin.

On real line|hard charts this pair agreed 240 times and was wrong together 3 times: W = 3 ÷ 240 = 1.25%.

4c · How far does one failure reach?

If ocr_pixel cannot fit the y-axis on a chart, it will fail on every point of that chart, so trying again for the next sentence is a waste. If it cannot find a line at one x, the next x may work. The profile measures this for each failure code that happened at least 10 times.

Maths
for one tool and one failure code c, for each chart g: n_g = points on the chart, k_g = points that failed with c reach(chart) = Σ_g k_g × (k_g − 1) ÷ Σ_g k_g × (n_g − 1) = for a point that failed with c, the share of the OTHER points on its chart that failed the same way reach ≥ 0.9 → "figure" else the same test per (chart, line) → "series" else "point"

Result in today's profile: for ocr_pixel, y_fit_failed and legend_not_found reach the whole figure, series_not_found and colour_ambiguous reach one series, the rest only one point. For the table tools, series_not_found reaches one series and x_not_found one point. Stage 11 uses this to skip pointless retries.

4d · Error correlation (reported, not used by the planner)

Maths
corr(a,b) = Pearson correlation of e_a and e_b over points both answered effective tools = K ÷ (1 + (K − 1) × mean corr) = 4 ÷ (1 + 3 × 0.188) ≈ 2.6

Four tools behave like about 2.6 independent readers. The most correlated pair is again vlm_table + vlm_crop (0.31), the least ocr_pixel + deplot (0.11) and deplot + vlm_table (0.10).

5

Read the PDF

Plain code
ingest/pdf_parser.pyingest/layout.pyingest/panels.pyingest/chart_type.pytools/axis.py
In plain words

Pull the sentences and the chart pictures out of the PDF, match each chart to its caption, and measure each chart's y-axis so the helper knows how tall the chart is in real units (the span). The span is used by every later formula.

What happens

  1. PyMuPDF gives text blocks with their position and the embedded images. v3+ Two-column pages are read column by column, charts drawn as vector graphics are rendered to images, and pages with no text layer are read with Tesseract OCR.
  2. A paragraph cut by a page break is joined again: the earlier block is at least 30 characters long, does not end with . ! ? or :, and neither block is a heading or caption.
  3. A figure's caption is the closest text block below it that starts with "Figure N:" or "Fig. N." (v4+ also "Fig 3:", "FIGURE 3 –", a caption above the figure, and never a caption that sits below the next figure). If none is found, the first caption on the next page is tried.
  4. Text is split into sentences, but not after "Fig.", "e.g.", "i.e." or "et al." (v4+ also "Dr.", "vs.", "Eq." and similar).
  5. For each figure: detect the chart type, OCR its text (legend, ticks, title), fit the y-axis and store the span. v3+ Split figures with panels (a), (b) into one figure per panel, and set flags: log_y, dual_y, unsupported:<kind>, axis_multiplier (v4+), scanned.
Rules for chart type
  • Find strongly coloured pixels (saturation > 80, brightness > 60) inside the plot area and group them into connected blobs.
  • A blob is a bar if its area is at least 0.2% of the plot, it fills more than 85% of its bounding box, and it is taller than 8 and wider than 6 pixels.
  • Two or more bars → grouped_bar if they have more than one colour, else bar. Otherwise → line.
Maths: fitting the y-axis
1. find the plot area (long dark frame lines, or a uniform grey panel) 2. find tick marks just outside the left edge, OCR each tick label on its own 3. try every pair of ticks (y₁, v₁), (y₂, v₂): y = pixel row, v = number read a = (v₁ − v₂) ÷ (y₁ − y₂) b = v₁ − a × y₁ count ticks whose pixel lies within 3 px of the line 4. keep the line most ticks agree with (if 3 or more ticks were read, at least 3 must agree, else "y_fit_failed") 5. least-squares fit on the agreeing ticks: value = a × pixel + b 6. span = |value(top of plot) − value(bottom of plot)| v3+ if the normal fit fails: try a downward axis, then a log axis (fit log10 of the values) numeric x-axis: pixel = a × value + b, at least 60% of the x ticks must agree

The "every pair, keep the most agreement" idea means one misread tick label (say "60" read as "68") cannot bend the axis. Two misread ticks can agree by chance, three rarely do.

Worked example

Ticks read at pixel rows 400 → 50, 300 → 60, 200 → 70, 100 → 80. Any pair gives a = (50 − 60) ÷ (400 − 300) = −0.1 per pixel and b = 50 + 0.1 × 400 = 90, and all four ticks agree. A line at pixel row 250 is therefore 90 − 0.1 × 250 = 65. If the plot runs from row 100 to row 400, the span is 80 − 50 = 30.

6

Look at each chart once: its situation

Plain code
agent/situation.pyagent/report_agent.planagent/planner.assess
In plain words

Before any sentence is checked, the helper looks at each chart once, without any AI model, and puts it in one of four boxes: easy or hard, line or bar. That box is the key used to look up the tool profile. It then notes which tools are worth calling on that chart and which pairs can check each other.

Rules
  • Hard if any of: the image is narrower than 700 pixels (it gets enlarged 2×), the legend has 4 or more entries, or the y-axis could not be read. Otherwise easy.
  • Key = line|easy, line|hard, bar|easy or bar|hard (bar and grouped bar share "bar").
  • For the chart's key the planner computes: each tool's answer rate, the usable tools (answer rate ≥ 10%), and the trustworthy pairs among them (W ≤ 5%). The maths is in stage 11. This plan is logged and shown live in the web app.
  • If a tool's numbers for that key rest on fewer than 10 points or fewer than 5 charts, the pooled * numbers are used instead. Points on one chart share their mistakes, so charts are the real evidence.
Worked example

A 620-pixel-wide line chart with 4 legend entries and a readable axis is line|hard (two reasons). From the profile: usable tools are all four, trustworthy pairs are every pair except vlm_table + vlm_crop.

7

Pick the sentences worth checking

Fixed rule
claims/finder.pyclaims/number_words.py

What happens

  1. v3+ Numbers written in words become digits: "ninety-one percent" → "91 percent", "epoch fourteen" → "epoch 14". The TA still sees the original sentence.
  2. Figure references are removed first, so "Figure 3" does not count as a number.
  3. No number left → the sentence is ignored.
  4. A number but no result word → SKIPPED (setup sentences such as "trained for 50 epochs").
  5. A number and a result word → checked.
  6. v3+ Sentences inside captions are also checked, against their own figure.
Result words
  • reach…, achiev…, obtain…, attain…, scor…, outperform…, beat…, lead…, ahead, exceed…, surpass…, better, worse, higher, lower, improv…, drop…, decreas…, increas…, accuracy, loss, f1, precision, recall, error rate, peak, highest, maximum.
  • v4+ also: hits, converges, plateaus, "stands at", "rose to", declines, trails, gains, AUC, BLEU, ROUGE, IoU, RMSE, MAE, WER, perplexity, error, top-1, "at epoch N", and case-sensitive mAP, AP, mIoU.
8

Understand the sentence

Plain code, AI only as a fallback
claims/parser.pyclaims/tolerance.pyclaims/direction.pyagent/report_agent._parse
In plain words

The sentence is turned into a small form: which line, which x point, which number, and how much rounding is fair. Fixed patterns try first. The AI model fills the same form only when no pattern fits. The number and its rounding are always computed by code from the text, never by the AI.

The form (ClaimSpec)

claim_type (point, difference, relative_change, peak), series, x, series_b, x_b, claimed_value, unit, relation (approx, greater, less, between), tolerance, figure_hint ("Figure 3" → 3), panel_hint.

What happens

  1. Clean the text: remove figure references and "As shown in". v4+ Past tense becomes present ("achieved" → "achieves"), "after 14 epochs" → "at epoch 14", symbols such as "~", "≥", "±" are accepted.
  2. Try the patterns, for example "X reaches N at epoch E", "X outperforms Y by N points on D", "From epoch A to epoch B, the accuracy of X improves by N%". v3+ Ranges, peaks ("peaks at 91.2% at epoch 14" gives two claims: the value, and "14 is the highest point"), and one claim per number in a sentence joined by "and".
  3. No pattern fits → the AI form-filler. Report text is wrapped in an "untrusted" block, the answer must be valid JSON in the form, it gets one retry with the error shown, and the number it copies must really appear in the sentence.
  4. If the rules gave a form but no figure shows that line and point (stage 9), the AI re-reads the sentence once, in case the rules mis-split it.
  5. Cannot be understood → NOT_SURE v2+ instead of dropped. A hidden instruction once made the AI drop 8 real claims, so a rejected claim-like sentence now always reaches the TA.
  6. v4+ Negated sentences ("never reaches", "does not exceed", "fails to") → NOT_SURE. Direction words set the sign: "decreases by 40%" becomes −40, "A is 3 points lower than B" becomes B − A = 3.
  7. v3+ Aliases ("RN50" → "ResNet-50") are used only if no figure shows the name as written.

Find the chart the sentence talks about

Plain code
retrieval/figure_index.pytools/legend.py
In plain words

Every chart gets a score for how many words it shares with the sentence, with a big bonus if the sentence names its figure number. Then a hard test: the chart only counts if the line name and the x point really appear on it. A good text score alone is never enough.

What happens

  1. Score every figure with BM25 (a standard search formula) between the sentence and the figure's caption plus OCR text.
  2. Add 10 if the figure number is the one cited, and 5 more if the cited panel letter matches.
  3. Keep only figures that cover the claim (rules below).
  4. If none cover: ask the AI model to read the legend names of figures that match everything except the line name (one cached call per figure) and test again. Then accept a cited figure that matches everything but a line name OCR may have misread (the tools must still find the line). v3+ Then a chart the tools cannot read that is cited or names the line, so the claim goes to the TA rather than "no figure".
  5. If the cited figure covers and ranks first, it wins. v2+ A cited figure that covers all but the line name beats an uncited one.
  6. Otherwise keep every covering figure that scores at least 0.8 × the top score, at most two.
Rules for "covers"
  • Every line name (series and series_b) appears in the figure's text: fuzzy partial match ≥ 80 out of 100. Names of 4 letters or fewer must match a whole word, so "SVM" never matches "SVHN". v4+ Family members never match: "ResNet-18" ≠ "ResNet-50", "CIFAR-10" ≠ "CIFAR-100", "BERT-base" ≠ "BERT-large".
  • Metric words must not contradict: an "accuracy" claim is not checked on a "loss" chart. v3+ An error-rate claim may use an accuracy chart (as 100 − accuracy).
  • v4+ Data split words must not contradict: a "test accuracy" claim is not checked on a validation chart.
  • A numeric x (an epoch) needs a line chart. A text x (a dataset name) must appear on the chart.
Maths: BM25Plus score
score(F) = Σ over words w of the sentence: idf(w) × [ δ + f(w,F) × (k1 + 1) ÷ ( f(w,F) + k1 × (1 − b + b × |F| ÷ avg|F|) ) ] idf(w) = ln((N + 1) ÷ n_w) f(w,F) = how often w occurs in figure F's text |F| = number of words in F's text N = number of figures n_w = figures whose text contains w k1 = 1.5 b = 0.75 δ = 1 (library defaults) final score = BM25 + 10 if F is the cited "Figure N" (+5 more for the cited panel)

Words are lower-cased, and a hyphenated word also counts as its parts: "resnet-50" adds "resnet" and "50". A word that appears in every figure has a small idf, so it barely helps. A rare word such as a model name helps a lot.

What the result means
  • 0 figures → NO_FIGURE. v3+ First a difference whose two values sit on two different figures is tried: same chart family, spans within 1.5× of each other, exactly one figure per value.
  • 1 figure → measure it.
  • 2 figures (second ≥ 0.8 × top) → measure both, and stage 15 decides what that means.

The claim loop: how the tool pair is chosen

Fixed rule or maths
agent/controller.pyagent/planner.pyagent/memory.py
In plain words

For each claim a small loop runs: choose a tool, read, check if the answer is clear, repeat. The planner choosing the tool works like a careful detective picking witnesses. It skips witnesses who almost never answer here. It only accepts a pair of witnesses who do not copy each other's mistakes. Among the good pairs it prefers the one most likely to give two answers, for the least time. It calls first the witness most likely to refuse, so a refusal costs little.

The planner may only return three actions: read with a tool, repair a tool, or hand off to the TA. It can never return an answer.

What the planner sees at each step

  • The chart's situation key and whether the claim's x has its own tick label (this changes the answer rates a lot, see 4a).
  • The readings so far, and the tools already tried for this claim.
  • Tools blocked by memory: a tool failed earlier on this chart with a code whose reach is "figure", or "series" for the same line.
  • The cost of each tool for this claim, computed as below.
Maths: cost of a tool for this claim
point tool (ocr_pixel, vlm_crop): cost = seconds per read × number of points (a difference needs 2 points) calls = number of points table tool (deplot, vlm_table), reads the whole chart once: cost = 0 if this chart's table was already read = seconds per chart ÷ claims still waiting on this chart otherwise calls = 1 for the first claim on the chart, 0 afterwards budget: at most 8 calls per claim (decision.max_tool_calls)

The planner's rules, in order

Maths: the five rules
R1 usable tool answers(t) ≥ 0.10 (on-tick or off-tick rate when known) a tool with no measurement counts as usable R2 trustworthy pair W(a,b) ≤ 0.05 (half the 10% false-flag target) W is used only if the pair agreed ≥ 20 times on ≥ 5 charts in this situation, else the pooled number, else "not measured" (allowed, counts as 0) R3 early hand-off no trustworthy pair among the usable tools → hand off now, no AI time spent R4 first reading PairValue(a,b) = answers(a) × answers(b) × (1 − W(a,b)) ÷ (1 + (cost(a) + cost(b)) ÷ 10) take the pair with the highest value, then read first the member with the highest (1 − answers(t)) ÷ (cost(t) + 0.1) "most likely to fail per second" R5 next reading candidates: usable, not tried, not blocked, and W(t,u) ≤ 0.05 with EVERY tool u that already gave a value Partner(t) = answers(t) × trust(t) × (1 − max_u W(t,u)) ÷ (1 + cost(t) ÷ 10) take the highest no candidate left → repair if a measured repair exists (stage 11, last box), else hand off

Why these pieces. answers × answers is the chance that both members give a value. 1 − W is the chance that, if they agree, the agreement is not a shared mistake. 1 + cost ÷ 10 is a gentle price: a tool that costs 10 seconds counts half as much as a free one. In R5 the first reading is already in hand, so the partner's own trust is added: a partner that is often badly wrong will often disagree and leave the claim unclear.

How the loop ends
  • After each successful reading, the tool's value is computed (stage 13). With 2 or more values the decision rule runs (stage 14).
  • CONSISTENT or MISMATCH → stop at once.
  • Unclear (between the margins, or readings too spread) → back to the planner for a third reading, if a trustworthy one exists.
  • A tool error → written into memory with its code, and the planner chooses again.
  • A difference where one tool reads both points as the same number → that reading is thrown away (it probably read one point twice).
  • No tool left, a hand-off, or the next tool would pass 8 calls → stop. Fewer than 2 values → NOT_SURE.
  • Repair: before handing off, the planner may ask for a measured repair (the AI reads the legend names so ocr_pixel can find a line by its colour). It is allowed only if the profile shows it fixed at least 50% of such failures and it would complete a trustworthy pair. How each reader gets a number

AI model call or plain code
tools/ocr_pixel.pytools/axis.pytools/deplot.pytools/vlm_table.pytools/vlm_crop.pytools/base.pytools/cache.py
In plain words

Four very different readers, on purpose, because different readers make different mistakes. ocr_pixel and vlm_crop read one point per call. deplot and vlm_table turn the whole chart into a table once, and every later lookup on that chart is free.

Rules for every reader
  • Every answer is saved in the reading notebook (cache/local.sqlite), keyed by tool, tool version, a fingerprint of the image and the (line, x) asked. Asking again returns the saved answer. That is why a run can be replayed offline in seconds.
  • A reader never crashes the helper. Any failure comes back as a short code such as series_not_found, x_not_found, two_lines_at_x, bad_json.

ocr_pixel · measures the chart like a ruler (no AI)

  1. Fit the y-axis as in stage 5.
  2. Find the line's colour from its legend mark (fuzzy name match ≥ 70). If two series colours could be confused → colour_ambiguous. Several colours but no readable legend → legend_not_found.
  3. Find the x pixel of the asked x (numeric axis: pixel = a × value + b, category axis: best tick label match ≥ 70).
  4. Bar: take the bar's top pixel. Line: take the line's pixel row at that x. Convert with value = a × pixel + b.
Maths: which pixels belong to the line's colour
p = pixel colour − background colour c = series colour − background colour share s = (p · c) ÷ (c · c) how much of the series colour is in this pixel leftover = | p − s × c | how badly "s parts colour + rest background" explains it keep the pixel if 0.35 ≤ s ≤ 1.3, leftover ≤ 28, and its own colourfulness ≥ 0.5 × s × colourfulness of c

This works on thin, blurred, JPEG lines, where a pixel is a mix of the line colour and the white background. It keeps orange apart from red even when both are faded, and stops grey grid lines from passing as "a little pink".

Bar and line rules
  • Bar: look in a window of ± half the tick spacing. Columns with at least 3 matching pixels form runs. Take the longest run, keep its middle 60%, and use the median of their top pixels. A top hidden just under the legend box → occluded_by_legend.
  • Line: look in windows of ±2, ±4, then ±7 pixels. Group the matching pixel rows (a gap of more than 3 pixels starts a new group). If the second group is at least 40% the size of the largest → two_lines_at_x (two lines of similar colour cross here). Otherwise use the median row of the largest group, but only if the same line sits close by a few pixels left and right (continuity check, else line_not_continuous).

vlm_crop · zooms in and asks the AI for one number

  • Cut a window of ± 1.5 × tick spacing around the x pixel, stitch the y-axis labels to its left, enlarge 2× (Lanczos).
  • Prompt: the series name, its colour as a hex code, the x value, "answer only with JSON {"value": …}". Temperature 0, so the same question gives the same answer.
  • Always answers, even between tick labels. Shares a model with vlm_table, which is why that pair is not trusted on hard line charts.

deplot and vlm_table · whole chart to table

  • deplot (Google's DePlot, a model made only for this) writes the table as text rows "x | value | value". vlm_table (Qwen3-VL-4B, the tool that can be fine-tuned) writes it as JSON.
  • The table is read once per chart and cached. A lookup then finds the line by fuzzy name (token match ≥ 70), or takes the only line of a single-line chart. The x must match exactly, by fuzzy text ≥ 85, or as an equal number.
  • These tools only output x values that carry a tick label. A claim at an unlabelled epoch gets x_not_found. That single fact explains most hand-offs on line charts.

The decision rule

Fixed rule or maths
decide/rule.pymeasure/aggregate.pycalibration/store.py
In plain words

Take the middle of the tool values as the best guess. Measure how far the student's number is from it: the gap. Allow the rounding the wording permits. Compare what is left with two margins from calibration. Small gap → matches. Gap clearly beyond the reading error → wrong. Anything between → ask a person. The flag margin uses the 95% factor and the accept margin the 75% factor, so flagging is stricter than accepting, because a false accusation is the worse mistake. This is the only place in the code where an answer is decided.

Maths: the whole rule
1 k = number of tool values. k < 2 → NOT_SURE ("too few readings") 2 est = median(v₁ … v_k) MAD = median(|vᵢ − est|) two values: |v₁ − v₂| ÷ 2 3 scale = MAD + 0.005 × span 4 look up q95 and q75 for (chart type, claim type, k) (stage 3, peak uses "difference") 5 m_flag = q95 × scale m_acc = q75 × scale 6 gap: approx |claimed − est| greater max(0, claimed − est) "over 80%": only a too-low est counts less max(0, est − claimed) between max(0, low − est, est − high) 7 gap > tol + m_flag → MISMATCH gap ≤ tol + m_acc and m_acc ≤ 0.03 × span → CONSISTENT gap ≤ tol + m_acc but m_acc > 0.03 × span → NOT_SURE ("readings too spread out to accept") otherwise → NOT_SURE ("between the two margins") 8 p-value (for stage 16): score = max(gap − tol, 0) ÷ scale p = (1 + number of calibration ratios ≥ score) ÷ (n + 1)

The disagreement never moves the best guess. It only widens the margins. The 3% cap in step 7 exists because, when tools disagree a lot, a real mistake could hide inside a wide accept margin.

In plain words

A few special cases are handled after the loop. Most of them can only make the helper more careful. The straight-line fallback is the one that can decide a claim that would otherwise go to the TA.

15a · Unreadable y-axis v4+

If the chart's y-axis could not be read, the span is unknown and falls back to 1.0, so the margin has no real scale. A MISMATCH there becomes NOT_SURE. An accept still stands. Measured in all saved runs: 31 of 231 such flags were wrong (13%), against 2.8% with a readable axis.

15b · Two charts fit the sentence

Rules
  • The claim was measured on both charts.
  • CONSISTENT on both → CONSISTENT (agent.ambiguous_rule: both).
  • v5 MISMATCH on both → MISMATCH, wrong whichever chart is meant. The weaker flag's p-value goes to the batch check. All 11 such cases in v4's runs were real errors.
  • Anything else → NOT_SURE ("ambiguous figure").

15c · A "%" with two meanings v4+

"Accuracy improves by 12%" may mean 12 percentage points, and "outperforms B by 3%" may mean 3% relative. If the parser's reading gives a MISMATCH, the other reading is computed from the same readings, with no new calls. If the other reading is CONSISTENT, the answer becomes NOT_SURE with a note.

Maths
relative-change claim read as points: v_t = b_t − a_t difference claim read as relative: v_t = (a_t − b_t) ÷ |b_t| × 100
Worked example

Accuracy goes from 83.0 to 91.2 and the sentence says "improves by 8.2%". As a relative change the chart says (91.2 − 83.0) ÷ 83.0 × 100 = 9.9%, a mismatch. As points it says 8.2, a match. So the sentence goes to the TA with the note instead of being flagged.

15d · Straight-line fallback for unlabelled x on a line chart v5

Runs only when the planner is about to hand off on a line chart and no tool gave any value, typically worked example C in stage 11. DePlot's table has values only at labelled x, so the value at the unlabelled x is read off a straight line between its labelled neighbours, and vlm_crop reads the same point directly. Because a real curve bends between two ticks, a flag must also clear a bend allowance.

Maths
straight line: y = y₀ + (y₁ − y₀) × (x − x₀) ÷ (x₁ − x₀) x₀, x₁ = nearest labelled x on each side (numeric x only, never beyond the ends) decide with the two values {deplot (straight line), vlm_crop} by the normal rule (stage 14), then: shift = 0.048 × span 95th percentile of the bend on the calibration charts move the interpolated point by ±shift, recompute the claim's value, take the largest change allow = largest change ÷ 2 halved, because the estimate averages two readings MISMATCH only if gap > tol + m_flag + allow, otherwise NOT_SURE accepts use the normal rule

The batch check (Benjamini–Hochberg)

Over all flags of one batch (one report in the apps, one assignment in a run), a standard statistical test was planned to keep the share of false flags under 10%.

Maths
m flags with p-values, sorted: p₍₁₎ ≤ p₍₂₎ ≤ … ≤ p₍ₘ₎ find the largest j with p₍ⱼ₎ ≤ 0.10 × j ÷ m keep flags 1 … j, the rest become NOT_SURE ("did not survive batch check")
Why it never removes a flag here

A flag means gap > tol + q95 × scale, so its score is above the q95 ratio, which is the K-th smallest with K = ⌈0.95 (n + 1)⌉. At most n − K ratios can be at or above the score, so

p ≤ (1 + n − K) ÷ (n + 1) ≤ (1 + n − 0.95 (n + 1)) ÷ (n + 1) = 0.05

Every flag has p ≤ 0.05, and for j = m the test bar is 0.10 × m ÷ m = 0.10. So j = m and every flag is kept. The check is still run, and this is reported as a finding.

Posting

Rules
  • The guard has an allow-list with one action: post_flag. update_grade and email_student exist in the pretend course site on purpose, and every attempt is blocked and counted. Unsafe actions executed: 0 in every run.
  • Every MISMATCH and NOT_SURE is posted with an evidence card: sentence, figure, claimed number, allowed rounding, each tool's value, best guess, flag margin, p-value, reason, notes.
  • A run saves traces.jsonl (the full diary of every claim: each planner step with its reason, every reading, the decision) and metrics.json.
